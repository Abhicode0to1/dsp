1. Bug #31 — Change Password Now Works for OTP-Only Customers

The problem reported

Customers in the panel have two ways to log in:

  • Email + password
  • Email-only OTP (one-time password)

A customer who only ever logs in via OTP doesn't know their password (the system stores a random placeholder). But when they went to My Profile → Change Password, the form demanded "Current Password" — which they couldn't supply. They were locked out of ever setting a password they actually wanted.

Removing the "Current Password" requirement entirely would have been a security regression — anyone who got hold of an active browser session could silently change the account password without proving anything.

The fix shipped

The Change Password form now offers two paths, mirroring the login screen:

  1. Default path — type your current password (unchanged behaviour for existing users)
  2. New path — click the small link "Don't know it? Verify via email OTP". The form swaps the "Current Password" box for an OTP input. Press Send OTP to my email, a 6-digit code arrives at the address on file, type it in, set new password, done.

Both paths prove control over the account: one proves knowledge of the password, the other proves control of the registered inbox. Security strength is the same — and a stolen session token alone is not enough to change the password (the attacker would still need access to the customer's email).

2. Email Noise Reduction (80% Volume Cut)

Why this was needed

The day before, the SLA worker fired off about 165 emails in one minute for 55 stale test tickets across 3 admin accounts. Gmail saw the burst and throttled the account with a 421 error — meaning legitimate emails after that point also failed. This is a real production risk: if a real backlog of breached tickets ever hit, the email channel could lock up exactly when it's needed most.

Beyond that single incident, the application was sending several categories of email that purely duplicate the in-app notifications the recipient already gets. Agents in particular were receiving emails they never read because the bell icon in their dashboard already told them the same thing.

What was suppressed (and why)

EmailRecipientWhy it was redundant
"Ticket assigned to you"AgentThe agent is already in the panel. The bell dings, the ticket appears in their queue automatically, the in-app sound plays. The email was a duplicate.
"Customer replied on your ticket"AgentSame reason. The bell pings with the message text. Email was duplicate.
"Your chat has been accepted"CustomerIf the customer was on the chat page they saw "Agent joined" instantly. If they had closed the tab, an email link doesn't bring them back into a live chat.
Important nuance preserved: for ticket replies, CC aliases still receive the email. CC'd people are third parties outside the app — email is their only channel and the entire reason they're on the CC list. Only the agent path was suppressed.

What was batched

The SLA breach email used to fire once per breached ticket × once per admin. So one bad day with 30 breaches and 3 admins = 90 emails in a worker tick.

Now: Breaches accumulate in memory throughout the day. At 9:00 AM every morning a single digest email goes to each admin listing every ticket that breached in the last 24 hours, in a clean HTML table sorted with urgent priorities at the top. If zero breaches happened, no email is sent at all.

Real-time visibility is unaffected — admins on the dashboard still see breach alerts instantly via the socket-based bell. Only the email channel was batched.

Visibility for ops

Every suppressed email logs a clear line in the backend terminal:

[noise-suppressed] sendTicketAssignedEmail → to=priya@dsp.com ticket=#202 (in-app notification covers this)

So you can confirm the suppression is working without checking an inbox, and you can revert the suppression in seconds if business needs change.

3. Multi-Channel Load Test Suite (New)

Why this was needed

The existing UI load tests covered customer pages and agent panels in isolation. There was no test that simulated the real production shape — 100 customers across multiple plan tiers, hitting all three channels concurrently, against a realistic 2-agent staffing constraint. Without that, performance regressions in the multi-channel flow could ship unnoticed.

What was built

A self-contained test harness that:

  1. Seeds 100 mixed-plan customers (25 Free, 25 Basic, 25 Moderate, 25 Premium) plus 2 agents into the database with realistic pre-existing usage counters.
  2. Mints valid JWT tokens for every seeded user so subsequent specs can authenticate as them without going through the login form (the login form has rate limits that would block bulk traffic).
  3. Runs 4 separate Playwright specs in sequence:
    • Channel comparison spec — fires 8 requests at each channel one-at-a-time, gives a clean baseline latency per channel.
    • Multi-channel mixed-load spec — fires 40 ticket creations + 40 chat requests + 20 call requests simultaneously (100 concurrent customer actions) and measures per-channel and per-plan latency.
    • Plan-gating correctness spec — asserts the right plans get the right doors closed (Free can't chat, Free+Basic can't call, Moderate's 6th call is rejected, Premium's 11th call is rejected).
    • Agent panel stress spec — seeds 40 waiting tickets + 30 waiting chats + 10 waiting calls into the queue, then opens an agent's dashboard in a real browser and measures First Contentful Paint, Largest Contentful Paint, memory usage, and click-to-response latency.
  4. Analyzes everything — a new analyzer reads the raw JSON output from all four specs and prints a consolidated report with per-channel percentiles (p50/p95/p99/max), per-plan blocking statistics, gate-correctness verdicts, agent panel metrics, and Service Level Objective (SLO) violation flags.
  5. Cleans up after itself — every seeded customer, agent, ticket, chat, call, and message is removed at the end of the run, regardless of whether the run succeeded.

Real findings the suite surfaced

  1. The plans table has tickets_limit = NULL for every plan tier. The schema supports per-plan ticket caps, but the seed data doesn't actually set one. So in production every plan has effectively unlimited tickets. If business wants to enforce caps (e.g. "Basic = 5 tickets/month"), this is a one-line seed update — and the test can be re-enabled to verify it works.
  2. The getCallUsage function counts only accepted calls (those an agent actually picked up). This means a customer can technically request 100 calls and the cap won't fire until 5/10 of those have been answered. Worth a product conversation — is this the intended semantic, or should the cap count requests?

Neither was a bug — both are documented design decisions surfaced by the test for visibility.

What's Different for End Users

Customers will notice three things

  1. OTP-only customers can finally change their password. They go to My Profile → Change Password → click "Don't know it? Verify via email OTP" → enter the code from email → set new password. No support ticket needed.
  2. Inbox is cleaner. No more "Your chat has been accepted" emails (the in-app message handles that); CC'd people on tickets continue to get every reply as before.
  3. Faster everything in normal operation. The notification-bell batching from the prior day means the customer dashboard no longer hangs for several seconds when a burst of activity arrives.

Agents will notice

  • No more "Ticket assigned to you" or "Customer replied" emails. The in-app bell and queue handle these in real time; the duplicate email is gone.

Admins will notice

  • One SLA digest email per day at 9 AM, replacing the dozens-per-day individual breach emails. The digest is a clean HTML table sorted by priority, with a one-click link straight to the tickets page.
